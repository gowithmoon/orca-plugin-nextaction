# 依赖延迟按完成历史计时，缺少记录时立即放行

依赖延迟的起算日取被依赖任务完成历史中最后一条记录的逻辑日："全部"模式取已完成的被依赖任务中最晚的，"任一"模式取最早的。只有经由插件完成的任务才有记录；没有记录的已完成任务（在 Orca 中直接改成已完成）和失效依赖，都视为早已完成："全部"模式下不参与"最晚"，"任一"模式下只要有一条这样的满足项就立即放行。宁可早放行，也不让任务因为一个算不出来的起算日被永远挡住。

## Considered Options

- 读取任务块的修改时间作为完成日：被否决。修改时间随任何编辑变化（改备注、加标签都会刷新），不能代表完成的那一天；而且它是时刻，换算逻辑日还要再猜一次日界线。
- 没有记录时不放行，直到用户经由插件重新完成一次：被否决。用户在 Orca 里直接改状态是正常用法，这样任务会无声地消失，用户不知道原因。
- 在任务上另存一个"依赖满足日"：被否决。它要在每个被依赖任务完成时去写所有依赖它的任务，写入范围大，还会进入用户的撤销历史；完成历史已经记下了需要的信息（ADR 0001，笔记是唯一数据源）。

## Consequences

- 被依赖任务完成后又在 Orca 中被直接改回、再改成已完成，最后一条记录是旧的，放行会提前。这是已知局限。
- 只有已完成的被依赖任务参与计时：改回未完成的任务即使留有旧记录，也不算满足。
- 延迟期内的任务处于依赖阻塞，原因种类为依赖延迟，带上放行日和起算的被依赖任务；它和依赖阻塞一样从祖先任务向下传递（ADR 0015）。循环依赖检测不看延迟。
- 依赖延迟与重复任务的配合（重复任务重置后怎么算）留给第八步。

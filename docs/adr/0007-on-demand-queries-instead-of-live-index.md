# 视图按需查询，用命令后钩子让缓存失效

视图按需查询，加上会话内的短期缓存，不维护全量的实时任务索引。缓存在三种时机失效：插件自己写入之后；Orca 的命令后钩子（`orca.commands.registerAfterCommand`）报告了与任务有关的编辑命令之后（如 `setBlocksContent`、`setRefData`、`insertTag`、`removeTag`、`setProperties`、`deleteBlocks`、`moveBlocks`、`undo`、`redo`）；视图打开、获得焦点或用户手动刷新时。钩子只负责通知缓存"可能有变化"，不根据命令参数维护数据，也不改变命令的行为。实测表明，这些钩子能收到用户在任意面板中的编辑、撤销，以及插件自己的写入；而重新查询足够快：条件查询 1–2 ms，取回并解码 1000 个任务约 70 ms（`docs/spikes/block-change-signals.md`、`docs/spikes/tag-property-query.md`）。

## Considered Options

- 在内存中维护全量任务索引，根据命令参数增量同步：被否决。撤销的钩子不带参数，同步带来的修改是否触发钩子也没有验证，增量同步一旦覆盖不全就会悄悄出错；而全量重新查询已经足够快。
- 注册 `orca.refresh-blocks` 广播的处理器：被否决。这个广播没有公开文档，而且 Orca 自己已经注册了处理器，插件再注册可能会把它顶替掉。
- 只在视图获得焦点时刷新（本 ADR 的初版）：被取代。命令后钩子经实测可靠，能让已打开的视图及时更新。

## Consequences

- 钩子监听的命令是一份清单，Orca 升级后要复查。
- 同步（S3 等）带来的修改是否触发钩子没有验证，所以"获得焦点时重新查询"仍然保留，作为兜底。
- 任务索引仍然是 `infra` 层接口背后的一个实现，以后换实现时上层代码不用改。

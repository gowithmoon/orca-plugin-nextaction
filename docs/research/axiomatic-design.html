NextAction 公理设计分析

分析对象：orca-plugin-nextaction 1.x，main 的 ed4a836（2026-11-27），F4 按 #249 改后的状态更新。 依据：README.md、GLOSSARY.md、docs/ARCHITECTURE.md、docs/adr/，以及 src/ 中各模块的 import 关系。

1. 方法

公理设计（MIT，Nam P. Suh）把设计写成功能需求 FR 到设计参数 DP 的映射 {FR} = [A]{DP}。 矩阵元素 Aij 表示设计参数 DPj 的改动是否影响功能需求 FRi。

  • 独立公理：各 FR 应能独立满足。矩阵为对角阵时是非耦合设计；能排成下三角阵时是解耦设计（按顺序调整 DP 即可）；其余是耦合设计。
  • 信息公理：满足独立公理的方案中，信息量最小（满足 FR 的概率最高）的最好。

本文把 DP 落到代码模块上，Aij 的依据是 FRi 对应的代码是否 import 了 DPj 的模块，或某条 ADR 规定了两者联动。 X 表示行为上的依赖（调用函数、遵守联动规则），x 表示只依赖类型定义。

2. 顶层需求与约束

FR0：让用户在虎鲸笔记里按 GTD 方法管理任务，随时知道此刻该做什么。
DP0：一个以笔记为唯一真相源、按 domain / application / infra / ui 分层的 Orca 插件。

约束（C）不属于 FR，它们限定 DP 的取值范围，不进入矩阵：

编号约束来源
C1笔记是唯一真相源，插件卸载后任务数据完整留在笔记里ADR 0001
C2任务只由任务标签识别，父子关系只来自块层级ADR 0002、0003
C3写入经活动面板的编辑器，能进入 Orca 的撤销历史ADR 0014、0024
C4业务规则是纯函数，当前时间由 Clock 传入ADR 0004
C5数据结构只增不改；写进笔记的名称在创建时确定ADR 0008、0009
C6插件不自己连接 AI 模型，只经 Orca 内置 AI 起草ADR 0026

3. 第一层分解：FR 与 DP

行和列按相同顺序排列：被依赖的基础模块在前，集成它们的功能在后。排成这个顺序后，对角线以上的格子就是耦合。

DP1–DP3 三列几乎全满：每个功能都要算日期、读 Task、经仓储读写。这是分层架构的正常形态，它们处在下三角，不构成耦合，但改动它们会波及所有 FR，所以 ADR 0008 要求数据结构只增不改。

5. 对角线以上的格子

F1　重复任务与常设排期互相依赖（FR7 ↔ DP10，真实耦合）

常设排期只对重复任务生效，domain/task/standing-schedule.ts 调用 activeRule、isNotAdvanced 判断今天该不该带进来（下三角 A10,7）。 反过来，去掉重复规则时要在同一次写入中去掉常设排期，set-recurrence.ts 调用 checkStandingSchedule（上三角 A7,10）。两个 DP 的改动互相波及，无论怎么排序都消不掉。

评价：这是 ADR 0029 有意做的取舍，那份 ADR 否决了把时段并进重复规则，并写明"将来要让非重复任务也能用，要先改这条"。耦合面只有一个函数调用，建议保持。 如果以后允许非重复任务使用常设排期，去掉规则时不再需要清理时段，A7,10 随之消失。

F2　项目与下一步行动看似互相依赖（FR4 ↔ DP8，分解粒度造成）

项目状态决定任务能否进入下一步行动（A8,4）；项目列表又要标出"缺少下一步行动""长期无进展"，并按 projectScore 排序（A4,8、A4,7）。

评价：代码里已经解耦。domain/project 只依赖 domain/task 和 domain/time，不碰阻塞和评分；健康提示在 application/usecases/project-nodes.ts 和 read-project-list.ts 里算。 第一层把"项目健康"归进 FR4，才显得耦合。按下面的第二层分解把它拆出来，排到下一步行动之后，矩阵就是下三角。

F3　Task 模型带着提醒、重复、回顾的类型（FR2 ← DP6、DP7、DP11，类型级）

domain/task/task.ts import 了 ReminderRead、RecurrenceRead、ReviewRead。Task 是聚合，需要持有这些属性的读取结果（包括"读不出来"的情况）。 只依赖类型，且 ADR 0008 让这些结构只增不改，建议接受。

F4　CalendarDate 定义在 Task 模型里（FR1 ← DP2，类型级）·已完成（#249）

原先 domain/time 的 calendar-days.ts、logical-day.ts、time-of-day.ts 都从 domain/task/task.ts 引用 CalendarDate，而 domain/task 的 my-day.ts、standing-schedule.ts、custom-property.ts 又引用 domain/time，两个模块互相引用。 已处理（#249）：CalendarDate 移到 domain/time/calendar-days.ts，task.ts 转发这个类型，调用方不用改。 现在 domain/time 不引用 domain 的其他模块，矩阵中的 A1,2 已删除，第一行只剩对角元素。

F5　任务关系图的节点带着完成历史和我的一天记录（FR5 ← DP7、DP10，类型级）

domain/blocking/task-graph.ts 的节点有 completionHistory、myDay 字段，供依赖延迟、我的一天、统计读取。任务关系图同时充当了"今天的读模型"。 只依赖类型，目前不必改；如果这张图继续长字段，可以考虑把各视图的附加信息从图结构里分出去。

6. 结论

独立公理：严格按第一层矩阵算，这是耦合设计。行为级的上三角格子只有 F1、F2 两处：F2 在第二层分解后消失，F1 是 ADR 0029 记录在案的有意耦合，只涉及一个函数调用。 其余上三角格子（F3、F5）都只依赖类型，F4 已在 #249 中消除。忽略类型级依赖、采用第二层的项目分解后，除 F1 外矩阵是下三角，整体接近解耦设计：按 DP1 → DP14 的顺序设计和修改，后面的功能不会反过来影响前面。

信息公理：几条 ADR 的取舍都在减少需要保持一致的状态，即降低信息量：常设排期靠计算不落盘（ADR 0029），视图按需查询不维护常驻索引（ADR 0007），重复任务复用同一个块（ADR 0006），父子关系只取块层级（ADR 0003）。

值得关注的：DP1–DP3（逻辑日、Task 模型、笔记存储层）是所有 FR 共用的地基，改动波及面最大。F4 已在 #249 中处理，DP1 现在不依赖其他任何 DP；其余的类型级耦合（F3、F5）建议保持。

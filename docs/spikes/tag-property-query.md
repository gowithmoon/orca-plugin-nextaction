# 技术验证：按任务标签属性查询的能力与性能

> Issue #13（同时完成 #5 移交的"能否在查询中直接排除孤立块"）。2026-10-07 在测试笔记库中运行（Windows，UTC+8），共两轮。测试数据：1007 个任务（1000 个平铺任务，6 个层级任务，1 个根级任务）。状态：**已完成**。

## 问题

- 按单选属性等于某选项（状态）筛选
- 按日期属性区间筛选，含属性为空的情况
- 按多选属性包含某值（上下文、标记）筛选
- 按数字属性比较（重要性、工作量）筛选
- 属性为空、不为空的判断
- 祖先、后代条件组能否表达"某任务的子任务""某块下的全部任务"
- 排序、分页的用法
- 返回结果中是否包含标签属性值，还是需要再取块
- 在 1000 个以上任务时各类查询的耗时

## 结论

### 返回结果

- **`query` 默认只返回前 20 条。** 要拿到全部结果，必须显式传 `pageSize`（第二轮 `default` 返回 20 条，`pageSize: 100000` 返回 1007 条）。第一轮几乎所有检查"失败"，就是因为这个截断。
- 返回的是**块 ID 数组**，不含属性值，属性值要再用 `get-blocks` 取。
- **出错时不抛异常，而是返回一个对象 `{ code: "SQLITE_ERROR" }`。** 所以每次查询都要检查返回值是不是数组。
- 条件里的属性不需要带 `type`、`typeArgs`，带不带结果都一样（第一轮两种写法对比）。

### 能用的条件（结果与实际数据完全一致）

| 需求 | 写法 | 检查项 |
|---|---|---|
| 全部任务 | `{ kind: 4, name: 标签 }` | Q0 |
| 状态等于 | `properties: [{ name: 状态, op: 1, value: "待开始" }]` | Q1 |
| 状态不等于 | `op: 2` | Q2 |
| 状态是几个值之一 | OR 组：`{ kind: 101, conditions: [标签+状态=A, 标签+状态=B] }` | Q3 |
| 数字比较、区间 | `op: 7`（>）、`9`（≥）、`10`（≤），同一属性写两条即为区间 | Q4、Q5 |
| 日期为空、不为空 | `op: 11`、`op: 12` | Q6、Q7 |
| 日期早于、区间 | `op: 10` / `op: 9` + `op: 10`，`value` 直接传 `Date` | Q8、Q9 |
| 多选包含某值 | `op: 3`，`value` 传字符串或数组都可以 | Q10、Q10b |
| 多选同时包含几个值 | `op: 3`，`value: [a, b]` | Q10c |
| 多选**不**包含某值 | 取反组：`{ kind: 100, negate: true, conditions: [标签+上下文 op 3 值] }` | Q11c |
| 多个条件同时满足 | 同一个标签条件里写多条 `properties` | Q12 |
| 某块下的所有任务（任意深度，可隔着普通块） | `{ kind: 102, conditions: [{ kind: 12, blockId }] }` | H1、H2 |
| 有未完成后代任务的任务 | `{ kind: 104, conditions: [标签+状态≠已完成] }` | H3 |
| 不在"将来/也许"任务下面的任务 | `{ kind: 102, negate: true, conditions: [标签+状态=将来/也许] }` | H4 |
| 排除根级块 | `{ kind: 9, hasParent: true }` | O1、O2 |
| 没有别名 | `{ kind: 9, hasAliases: false }` | O3 |

### 不能用或结果不对的写法

- **单选属性用 `op: 3` 传数组（"属于这几个值"）时，结果为空**（Q3b）。传单个字符串时等同于"等于"（Q3c）。要按几个状态筛选，用 OR 组。
- **多选属性的 `op: 4`（不包含）语义不对。** 它的实际含义是"存在一个不等于该值的选项"：同时有 `@home` 和 `@company` 的任务被算作"不包含 @home"，没有任何上下文的任务反而被排除了（Q11、Q11b）。要表达"不包含"，用取反组（Q11c）。
- **`sort` 不论传什么字段都返回 `SQLITE_ERROR`**，包括 `created`、`modified`、属性名，以及带 `_` 前缀的属性名。按 `QuerySort = [字段, 方向]` 的类型定义写的，原因不明。
- **`page` 参数看起来没有效果。** 不带排序时，`page: 0` 和 `page: 1`（都是 `pageSize: 100`）返回了完全相同的 100 条（`unsortedOverlap01: 100`）。可能是页码从 1 开始，或者分页必须配合排序使用。没有进一步验证。

### 性能（1007 个任务）

- 各类条件查询都在 **1–2 ms** 之内，包括层级查询和组合条件。
- 用 `get-blocks` 一次取回 1007 个块：**71 ms**；从中解码出全部属性值：**1 ms**。
- `get-blocks` 不会把块加载进 `orca.state.blocks`（前后都是 15 个）。
- 写入速度：`batchInsertText` 建 1000 个块用 57 ms；`batch-insert-tags` 每 50 个块打标签加属性值 10–30 ms，一共 395 ms。`batch-insert-tags` 是后端接口，不经过编辑器的撤销栈，文档要求调用方自己更新前端状态。

## 对后续步骤的影响

**第二步：查询构建（`infra/orca/query`）**
- 每次查询都显式传 `pageSize`（足够大），并检查返回值是不是数组；返回 `{ code }` 时转换成插件的错误类型。
- 只使用上表"能用的条件"中的写法。"几个状态之一"用 OR 组，"不包含"用取反组。这两种陷阱（Q3b、Q11）写进查询构建模块的测试里，防止以后被"简化"回去。
- **孤立块的排除直接写进任务查询**：加上 `{ kind: 9, hasParent: true }`。这解决了 #5 遗留的问题，不需要在编解码之后再过滤。
- 不使用 `sort` 和 `page`。

**第四、五、七步：视图**
- **排序和分页都在内存中做。** 1000 个任务取回加解码不到 100 ms，下一步行动的评分本来就要在 `domain/scoring` 中计算，排序跟着评分走。
- 视图的查询分两步：先用条件查询拿到候选 ID（毫秒级），再用 `get-blocks` 取块并解码。下一步行动的阻塞判断可以部分下推到查询（H3、H4），但最终以 `domain/blocking` 的计算结果为准，查询只用来缩小范围。
- 第七步的已完成任务数量可能很大。"展开时才查询"仍按 `docs/ROADMAP.md` 执行；如果实测发现量大时太慢，再回头研究 `page` 和 `sort` 的正确用法。

**写入**
- 面向用户的写操作仍然用编辑器命令（`insertTag`、`setRefData` 等），这样能撤销，界面也会同步更新。`batch-insert-tags` 只考虑用于以后的批量导入这类场景，届时再验证撤销和界面刷新。

## 验证代码

- 第一轮：`.scratch/spikes/13-query.js`（不纳入版本管理）。创建测试标签"NA查询测试"（状态、重要性、截止时间、上下文），在 2027-02-01 日记下的容器中用 `batchInsertText` 建 1000 个块，按 20 组用 `batch-insert-tags` 打标签，组合出 6 种状态 × 7 种重要性 × 4 种截止时间 × 3 种上下文；另外建 `P{C1, X{C2}, C3}`、`S{S1}` 的层级任务和一个根级任务 R。
- 第二轮：`.scratch/spikes/13b-query.js`。从笔记中读回实际数据，作为预期结果的依据；所有查询都带 `pageSize: 100000`；对不上时，按属性值统计漏掉和多出的任务。

## 实际返回（第二轮摘录）

返回结构：

| 写法 | 结果 |
|---|---|
| 不带 `pageSize` | 数组，20 条 |
| `pageSize: 100000` | 数组，1007 条 |
| 带 `sort`（任何字段） | `{ code: "SQLITE_ERROR" }` |
| `page: 0, pageSize: 100` | 数组，100 条 |
| 单选 `op: 3` 传数组 | 数组，0 条 |
| 单选 `op: 3` 传字符串 | 数组，204 条 |

检查（`pageSize: 100000`）：26 项中 23 项完全一致，耗时都在 1–2 ms。不一致的 3 项：
- Q3b（单选 `op: 3` 传数组）：预期 354，实际 0。
- Q11、Q11b（多选 `op: 4`）：预期 357，实际 650；多出 300 个同时有 `@company` 和 `@home` 的任务，漏掉 7 个没有上下文的任务。

性能：`queryAllMs: 1`，`getBlocksAllMs: 71`，`decodeMs: 1`，`stateBlockCount` 前后都是 15。

分页：带排序时全部失败（返回 0 条）；不带排序时，`page: 0` 与 `page: 1` 的结果重叠 100 条。
